# آموزش ۰۴ — ابزارهای داخلی

وقتی یک عامل dsh کار می‌کند، مدل به مجموعه‌ای از «ابزارها» دسترسی دارد — هر ابزار یک قابلیت مشخص با ورودی و خروجی ساختاریافته است. این آموزش، کاتالوگ کامل ابزارهای عرضه‌شده رسمی را به فارسی توضیح می‌دهد. منبع این آموزش، فایل تولیدشده [`docs/tool-catalog.md`](../dsh/docs/tool-catalog.md) در سورس پروژه است که به‌صورت خودکار از کد واقعی پلاگین‌ها ساخته می‌شود؛ یعنی آنچه اینجا می‌خوانید مطابق رفتار واقعی ابزارهاست، نه توصیف کلی.

## نمای کلی: نقشه بسته‌های ابزار

هر ابزار متعلق به یک بسته پلاگین است. جدول زیر خلاصه نقشه کامل است:

| بسته پلاگین | نام ابزار نزد مدل | کاری می‌کند |
|---|---|---|
| `dsh-tool-bash` | `bash` | اجرای دستورات shell در لینوکس/مک، با پشتیبانی اجرای پس‌زمینه |
| `dsh-tool-pwsh` | `pwsh` | همان bash برای ویندوز با PowerShell |
| `dsh-tool-fs` | `read`، `write`، `edit`، `read_image` | خواندن/نوشتن/ویرایش فایل، خواندن تصویر |
| `dsh-tool-str-replace-editor` | `str_replace_editor` | نمایاندن/ایجاد/جایگزینی دقیق متن/درج خط |
| `dsh-tool-fs-search` | `glob`، `grep` | جست‌وجوی نام فایل با الگو و جست‌وجوی محتوا (با ripgrep داخلی) |
| `dsh-tool-web` | `web_search`، `web_fetch` | جست‌وجوی وب و واکشی صفحه |
| `dsh-tool-subagent` | `subagent` (و `subagent_fork`) | تفویض وظیفه به عامل فرزند |
| `dsh-tool-subagent-control` | `send_message`، `interrupt_agent`، `list_agents` | مدیریت عامل‌های در حال اجرا |
| `dsh-tool-todo` | `todo_write` | نگه‌داری چک‌لیست وظایف نشست |
| `dsh-tool-jobs` | `job_list`، `job_output`، `job_kill` | مدیریت کارهای پس‌زمینه |
| `dsh-tool-schedule` | `schedule_create` و ۳ ابزار دیگر | زمان‌بندی پیام/کار در آینده |
| `dsh-tool-goal` | `create_goal`، `get_goal`، `update_goal` | تعریف و پیگیری هدف کلان |
| `dsh-tool-workflow` | `workflow` | اجرای گردش کار چندمرحله‌ای اسکریپتی |
| `dsh-tool-ralph` | `ralph` | چرخه‌های اجرای متمرکز روی یک هدف ثابت |
| `dsh-tool-terminal` | `terminal_open/read/send/...` (۶ ابزار) | ترمینال تعاملی ماندگار (PTY) |
| `dsh-tool-bash-persistent` / `pwsh-persistent` | `bash` / `pwsh` | shell ماندگار با حفظ وضعیت |
| `dsh-tool-lsp` | `lsp` | قابلیت‌های زبان‌محور (تعریف، ارجاع، خطاها) از LSP |
| `dsh-tool-skill` | `skill` | بارگذاری مهارت‌های آموزشی در مکالمه |
| `dsh-tool-ask-user` | `ask_user_question` | پرسیدن سؤال از کاربر در میانه کار |
| `dsh-plan-mode` | `exit_plan_mode` | خروج از حالت برنامه‌ریزی با ارائه طرح برای تأیید |
| `dsh-tool-present` | `present` | ارائه خروجی نهایی (دستیافتنی/Deliverable) به کاربر |
| `dsh-tool-working-directory` | `working_directory` | خواندن/تغییر پوشه کاری نشست |
| `dsh-tool-cordis` | `cordis_inspect_list`، `cordis_inspect_query` | بازرسی فقط‌خواندنی زمان اجرا (مدیریت توسعه) |
| `dsh-tool-executor-ptc` | `run_code` | اجرای کد برنامه‌نویسی‌شده (Programmatic Tool Calling) |
| `dsh-plugin-manager` | `plugin_manager` | نصب/فعال/غیرفعال کردن پلاگین‌ها و بسته‌ها |
| `dsh-plugin-market` | `plugin_market` | جست‌وجو و مرور بازار پلاگین |
| `dsh-mcp-resources` | `list_mcp_resources` و... | کار با منابع سرورهای MCP |
| `dsh-tool-session-query` | `session_search` و ۴ ابزار دیگر | جست‌وجوی فقط‌خواندنی در تاریخچه نشست‌ها |
| `dsh-tool-workspace-dependencies` | `load_workspace_dependencies` | بارگذاری وابستگی‌های فضای کاری |
| `dsh-action-cards` | `propose_action` | پیشنهاد اقدام به کاربر به‌شکل کارت تعاملی |
| `browser-use` (تجربی) | `stagehand_navigate` و... | کنترل مرورگر واقعی: ناوبری، اسکرین‌شات، استخراج داده |
| `computer-use` (تجربی) | ابزارهای کنترل رایانه | کنترل ماوس/کیبورد روی رومیزی |
| `agent-team` (تجربی) | `spawn_teammate` و... | تیم عامل‌ها با وظایف مشترک |

نکته: ابزارهای تجربی فقط در ترکیب‌های خاص فعال می‌شوند و بسته به پروفایل شما ممکن است نباشند.

## دسته ۱ — اجرای دستور و کار با فایل‌سیستم

### `bash` و `pwsh`
ستون فقرات عامل. دستور shell اجرا می‌کند و خروجی می‌گیرد. رفتارهای مهمی که باید بدانید:

- اگر رجیستری کارهای پس‌زمینه (`ctx.jobs`) ترکیب شده باشد، ابزار پارامتر `run_in_background` هم دارد؛ یعنی عامل می‌تواند دستور طولانی (مثل build) را در پس‌زمینه بگذارد و با ابزارهای `job_*` خروجی‌اش را دنبال کند.
- در ویندوز، پلاگین `pwsh` معادل PowerShell است؛ هر فراخوانی در پروسه تازه اجرا می‌شود (بدون PTY ماندگار) با مسیرهای بومی `C:\...` و متغیرهای `$env:NAME`.
- محیط اجرا توسط پلاگین `dsh-shell-env` مدیریت می‌شود (متغیرهای `DSH_*`).

### `read` / `write` / `edit` / `read_image`
ابزارهای اصلی فایل‌سیستم. سیاست مهم: «اول بخوان، بعد بنویس» به‌صورت پیش‌فرض توسط پلاگین `dsh-fs-observation-policy` اعمال می‌شود؛ یعنی عامل نمی‌تواند فایلی را بدون دیدن محتوایش بازنویسی کند — یک سپر خوب علیه خطاهای مدل. ابزار `read_image` تصویر را به‌عنوان پیوست دائمی ذخیره می‌کند و فقط وقتی مدل رouted واقعاً ورودی تصویر بپذیرد کار می‌کند.

### `glob` و `grep`
ابزارهای کشف. نکته فنی خوب: این دو ابزار باینری ripgrep را به‌صورت بسته‌بندی‌شده (`@vscode/ripgrep`) از طریق زیرپروسه اجرا می‌کنند — نه نیاز به نصب `rg` روی سیستم دارید و نه لایه shell درگیر می‌شود. نتایج فراتر از سقف، ذخیره و قابل پیگیری می‌شوند تا عامل بتواند ادامه دهد.

### `str_replace_editor` و ترمینال ماندگار
برای ویرایش‌های دقیق متنی (بازکردن نمای فایل، جایگزینی لفظی یکتا، درج خط) ابزار مستقل `str_replace_editor` هست که با هر shell سازگار است. برای کارهایی که وضعیت shell باید بماند (مثلاً ورود به یک محیط تعاملی مثل `python` یا `mysql`)، پلاگین‌های «پERSISTENT» ترمینال PTY واقعی می‌دهند: `terminal_open`، `terminal_read`، `terminal_send`، `terminal_close` و...

## دسته ۲ — وب و اطلاعات

### `web_search` و `web_fetch`
جست‌وجوی وب و واکشی صفحه. انتخاب «موتور/سرویس واقعی» پشت `ctx.web` پنهان است؛ یعنی می‌توانید backend را عوض کنید بدون آنکه schema ابزار برای مدل عوض شود (سازگاری پایدار). برای کاربران ایران: این ابزارها از سمت سرور شما به اینترنت وصل می‌شوند؛ اگر سرور محلی است، مسئله تحریم/پروکسی اینجا هم مطرح است (آموزش ۰۹).

## دسته ۳ — همکاری چندعاملی

### `subagent`
مهم‌ترین ابزار «مقیاس‌پذیری». عامل والد می‌تواند یک وظیفه را به یک عامل فرزند بسپارد؛ فرزند با نشست خودش کار می‌کند و نتیجه به والد برمی‌گردد. چند نکته دقیق از کاتالوگ رسمی:

- نام ابزار با پیکربندی قابل تغییر است (`toolName`؛ پیش‌فرض `subagent`).
- با فعال بودن `modelSelection` می‌توان مدل فرزند را هم انتخاب کرد؛ `modelDiscovery` فهرست مدل‌های قابل‌انتخاب را کشف می‌کند.
- هر تفویض فوراً شناسه فرزند را برمی‌گرداند؛ فرزندان محلی قابل پیگیری (follow-up) هستند.
- **مجوزدهی**: برای هر نشست سطح‌بالا، سیاست مجوز ثبت می‌شود و فرزندان به ارث می‌برند؛ بدون ثبت سیاست، فقط مسیر مدلِ والدِ فعلی مجاز است. یعنی فرزند نمی‌تواند پشت سر شما مدل دیگری را صدا بزند.

### `send_message` / `interrupt_agent` / `list_agents`
کنترل عامل‌های مدیریت‌شده: پیام به فرزند، قطع اجرای آن، فهرست عامل‌های زنده.

### تیم‌های عامل (تجربی)
پروفایل «Agent Teams» ابزارهایی مثل `spawn_teammate` و `team_task_create` می‌دهد که مدل‌های هم‌تیمِ دائمی با صندوق پیام و وظایف مشترک می‌سازند — شبیه یک تیم واقعی توسعه. به‌صورت پیش‌فرض غیرفعال است.

## دسته ۴ — نظم، زمان و هدف

### `todo_write`
چک‌لیست نشست. رابط‌های کاربری آخرین رخداد todo را به‌شکل لیست کارها نمایش می‌دهند. پیکربندی `allowParallelInProgress` تعیین می‌کند چند وظیفه هم‌زمان «در حال اجرا» مجاز باشد.

### `schedule_create` / `schedule_update` / `schedule_delete` / `schedule_list`
زمان‌بندی واقعی: پذیرش زمان مطلق، فاصله ثابت (`every_seconds`)، زمان‌های روزانه/هفتگی با منطقه زمانی IANA مشخص، و cron پنج‌فیلدی. پیام‌های سررسیدشده در همان نشست اصلی ادامه پیدا می‌کنند. مثال کاربردی: «هر روز ساعت ۸ صبح خلاصه تغییرات پوشه پروژه را برایم بنویس».

### `create_goal` / `get_goal` / `update_goal`
مدیریت هدف کلان با چرخه‌های pause/resume/complete/blocked. ساخت، ویرایش و مکث نیازمند اقتدار ریشه‌ی «انسان مستقیم» است — یعنی کاربر، نه عامل‌های فرزند.

### `workflow` و `ralph`
اجرای گردش‌کارهای ساختاریافته چندمرحله‌ای؛ `ralph` چرخه‌ای ثابت است که در هر دور یک فرزند تازه با هدف غیرقابل‌تغییر می‌سازد — برای کارهای متمرکز طولانی.

## دسته ۵ — تعامل با کاربر و برنامه‌ریزی

### `ask_user_question`
پرسیدن سؤال از کاربر در میانه اجرا. به‌صورت پیش‌فرض مسدودکننده است (منتظر پاسخ می‌ماند)؛ با `mode: timed` می‌تواند مهلت داشته باشد و در انتظار بماند تا پاسخ دیرتر هم بپذیرد.

### `exit_plan_mode` (حالت برنامه‌ریزی)
در حالت plan، مدل ابتدا برنامه می‌سازد و با این ابزار طرح را برای تأیید ارائه می‌دهد؛ شما یا تأیید می‌کنید یا با بازخورد ادامه برنامه‌ریزی را دیکته می‌کنید. برای کارهای بزرگ و پرریسک عالی است.

### `propose_action` (کارت‌های اقدام)
فقط وقتی به مدلِ بارگذارنده «مهارت» نوع کارت ثبت‌شده داده شود؛ به‌شکل کارت تعاملی پیشنهاد عملی می‌دهد.

### `present`
ارائه دستیافتنی‌ها (Deliverables) — خروجی‌های نهایی مثل فایل تولیدشده. در رابط وب، کارت‌های بازکردن فایل منبع هم می‌دهد.

## دسته ۶ — مدیریت پلاگین و بازار

### `plugin_manager`
لیست، فعال/غیرفعال، نصب بسته (bundle) و حذف آن. نکات مهم:

- هر اقدام نیازمند مجوز full-access یا تأیید همین فراخوانی است.
- نصب بسته می‌تواند اسکریپت‌های build مجاز را اجرا کند — یعنی نصب پلاگین = اجرای کد شخص ثالث؛ قبل از تأیید، سازنده را ارزیابی کنید.
- تغییرات روی تمام نشست‌های پروفایل اثر می‌گذارد.
- الزامات نسخه dsh (در `engines.dsh`) اگر برآورده نشوند، نصب را می‌بندند؛ «معافیت نسخه» ممکن است اما با ریسک خرابی و از‌دست‌رفتن داده — فقط با آگاهی کامل.

### `plugin_market`
مرور ایندکس‌های بازار پلاگین: فهرست ایندکس‌ها، جست‌وجوی بسته‌ها، دیدن نسخه‌ها. توجه: عنوان و توضیحات بسته‌ها «متن شخص ثالث» است و دستور نیست — مدل این را در توصیف ابزار می‌داند تا متن مخرب بازار به «دستور» تبدیل نشود. افزودن/حذف ایندکس فقط از طرف کاربر است.

## دسته ۷ — توسعه و بازرسی

### `cordis_inspect_list` / `cordis_inspect_query`
بازرسی فقط‌خواندنیِ درخت زمان اجرا (چه پلاگینی فعال است، چه سرویسی چه وضعیتی دارد). «حالت سازنده» (Creator mode) برای توسعه‌دهندگان پلاگین طراحی شده. تغییرات پایدار به‌شکل bundle ساخته و با plugin_manager نصب می‌شوند.

### `run_code` (PTC)
به‌جای صدازدن ابزارها یکی‌یکی، مدل یک «برنامه» می‌نویسد که چند فراخوانی ابزار را ترکیب می‌کند؛ فراخوانی‌های فرعی به خط‌لوله محافظت‌شده مشترک می‌روند و اجراهای موازی تا سقف `maxParallelSubCalls` هم‌پوشان می‌شوند. برای کارهای داده‌ای ترکیبی، به‌مراتب سریع‌تر و ارزان‌تر از زنجیره ابزارهاست.

### `lsp` و `load_workspace_dependencies`
ابزار LSP (پیشنهاد تکمیل، پرش به تعریف، فهرست خطاها) از طریق ارائه‌دهنده ثبت‌شده (مثل `dsh-lsp-stdio`) کار می‌کند؛ بدون ارائه‌دهنده، خطای ساختاریافته `LSP_UNAVAILABLE` برمی‌گردد نه خرابی.

### `session_search` و بقیه ابزارهای نشست
پنج ابزار فقط‌خواندنی برای جست‌وجو در تاریخچه نشست‌ها (رویدادها، ردگیری). برای «چرا عامل قبلی این تصمیم را گرفت؟» فوق‌العاده است.

## دسته ۸ — مرورگر و رایانه (تجربی)

### ابزارهای Stagehand
`stagehand_navigate`، `stagehand_screenshot`، `stagehand_extract`، `stagehand_act`، `stagehand_observe`، `stagehand_tabs` — کنترل واقعی یک مرورگر: باز کردن صفحه، عکس گرفتن، استخراج ساختاریافته داده، کلیک/تایپ. برای اتوماسیون وب‌سایت‌هایی که API ندارند.

### Computer-use
کنترل رومیزی (ماوس/کیبورد) — تجربی و حساس؛ فقط در محیط ایزوله استفاده کنید.

## جدول تصمیم: کدام ابزار برای کدام کار؟

| می‌خواهم... | ابزار مناسب |
|---|---|
| فایل‌های پروژه را بگردم | `glob` + `grep` |
| محتوای یک فایل را ببینم/عوض کنم | `read` → `edit` |
| یک دستور بسازم/تست‌ها را بگیرم | `bash` (پس‌زمینه طولانی‌ها با `run_in_background`) |
| اطلاعات روز را بگیرم | `web_search` + `web_fetch` |
| کار سنگین را موازی کنم | `subagent` |
| هر روز کاری خودکار انجام شود | `schedule_create` |
| یک هدف بزرگ را مدیریت کنم | `goal` + `todo_write` + plan mode |
| از کاربر سؤال بپرسم | `ask_user_question` |
| خروجی نهایی تحویل بدهم | `present` |
| چند ابزار را در یک قدم ترکیب کنم | `run_code` (PTC) |
| پلاگین نصب کنم | `plugin_market` → `plugin_manager` |
| رفتار زمان اجرا را ببینم | `cordis_inspect_*` |

## کدام ابزارها در پروفایل من فعال‌اند؟

دو راه بررسی:

1. در رابط وب، پلاگین‌های فعال و ابزارهای لحظه اجرا را در نشست‌ها می‌بینید.
2. از خط فرمان: `dsh --profile web --dump-config` — درخت کامل ترکیب پلاگین‌ها را چاپ می‌کند.

برای افزودن/کم‌کردن ابزار، پروفایل را ویرایش کنید یا با `dsh plugin --profile <name> add <package>` پلاگین نصب کنید (شرح کامل در آموزش ۰۶).
