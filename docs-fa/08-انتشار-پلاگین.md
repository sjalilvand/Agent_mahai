# آموزش ۰۸ — انتشار پلاگین

پلاگین شما ساخته شد و کار می‌کند؛ حالا می‌خواهید دیگران (یا سرورهای خودتان) هم استفاده کنند. این آموزش سه سطح انتشار را توضیح می‌دهد: نصب محلی در پروفایل، انتشار در npm، و دیده‌شدن در جامعه dsh. منبع اصلی: [مستند انتشار رسمی](../dsh/docs/user/develop/basic/publish.md).

## یادآوری معماری: باندل می‌فرستی، پروفایل نمی‌فرستی

- **باندل** چیزی است که شما می‌نویسید و منتشر می‌کنید: بسته npm با مانیفست `dsh.bundle` که یک فایل patch حمل می‌کند.
- **پروفایل** چیزی است که کاربر شما می‌سازد: ترکیب باندل‌ها در `$DSH_HOME/profiles/<name>`.
- سطرهای پچ داخل باندل، بسته را «با نام» صدا می‌زنند (نه مسیر نسبی) تا رزولوشن Node بعد از نصب، کد واقعی نصب‌شده را پیدا کند.

## سطح ۱ — نصب در پروفایل محلی

`dsh plugin` آرگومان‌ها را به pnpm در پوشه پروفایل فوروارد می‌کند؛ یعنی هر فعل pnpm کار می‌کند:

```sh
# نصب از پوشه محلی (چک‌اوت توسعه)
dsh plugin --profile web add ./hello-plugin

# نصب از رجیستری (بعد از انتشار)
dsh plugin --profile web add dsh-hello-plugin

# حذف
dsh plugin --profile web remove dsh-hello-plugin

# بررسی وابستگی
dsh plugin --profile web why dsh-hello-plugin
```

اولین استفاده، پروفایل را راه‌اندازی می‌کند. فهرست باندل‌های نصب‌شده در `package.json` پروفایل نگه‌داری می‌شود و لایه‌ها به ترتیب فهرست اعمال می‌شوند؛ لایه `cordis.patch.yml` شخصی کاربر همیشه آخر می‌آید و بالاترین اولویت را دارد.

⚠️ محدوده نسخه را در مانیفست باندل اعلام کنید — `engines.dsh` (مثلاً `">=0.2.0 <0.3.0"`)؛ نصب و بوت پروفایل، باندل ناسازگار را رد می‌کنند. اگر `engines.dsh` نگذاشته باشید، به‌جای آن محدوده‌های peer dependencyهای `@deepseek-ai/dsh*` بررسی می‌شوند.

## سطح ۲ — انتشار در npm

بسته شما یک بسته npm معمولی است؛ روند انتشار استاندارد است:

```sh
# ۱) فیلدهای حیاتی package.json را نهایی کنید
{
  "name": "dsh-my-plugin",            // قرارداد جامعه: پیشوند dsh-
  "version": "0.1.0",
  "type": "module",
  "main": "index.js",
  "files": ["index.js", "cordis.patch.yml"],  // فقط لازم‌ها را منتشر کنید
  "license": "MIT",
  "keywords": ["dsh-plugin"],          // برای کشف‌پذیری
  "engines": { "dsh": ">=0.2.0 <0.3.0" },
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}

# ۲) تست نصب محلی قبل از انتشار
npm pack                      # تاربال نهایی را می‌سازد
dsh plugin --profile web add ./dsh-my-plugin-0.1.0.tgz

# ۳) انتشار
npm publish
```

### نکات npm برای کاربران ایران

- برای انتشار، حساب npm نیاز به تأیید ایمیل دارد و سایت npm از داخل ایران گاهی محدود است؛ انتشار از یک سرور واسط یا با پروکسی انجام می‌شود (الگوی کامل در آموزش ۰۹).
- اگر رجیستری سیستم شما میرور ایرانی است، `npm publish` را صریح به رجیستری رسمی بزنید — میرورها فقط «خواندنی» هستند و انتشار را قبول نمی‌کنند:

```sh
npm publish --registry https://registry.npmjs.org/
```

- بعد از انتشار، تازگی بسته در میرورهای ایرانی ممکن است چند دقیقه تا چند ساعت تأخیر داشته باشد؛ در مستندات پلاگین، کاربران ایرانی را راهنمایی کنید که برای نصب نسخه تازه می‌توانند موقتاً رجیستری رسمی را با پروکسی استفاده کنند.

## سطح ۳ — دیده‌شدن در جامعه dsh

مسیرهای رسمی کشف‌پذیری که خود پروژه اصلی معرفی می‌کند:

1. **موضوع گیت‌هاب `dsh-plugin`**: به مخزن پلاگین خودتاپ موضوع (topic) `dsh-plugin` را اضافه کنید تا در جست‌وجوی موضوعی گیت‌هاب پیدا شوید.
2. **ایندکس‌های بازار پلاگین**: بازار پلاگین dsh از «ایندکس» — فهرست‌های منتشرشده از بسته‌ها — تغذیه می‌کند؛ هر ایندکس، بسته‌ها را با نسخه پیش‌فرض و هدف نصب معرفی می‌کند و کاربران با `plugin_market` جست‌وجو و با `plugin_manager` نصب می‌کنند. اگر ایندکسِ جامعهای راه‌اندازی کردید (مثلاً «ایندکس پلاگین‌های ایرانی dsh»)، کاربران می‌توانند URL آن را به تنظیمات بازار خود اضافه کنند.
3. **گیت‌هاب Discussions پروژه اصلی**: معرفی پلاگین و بازخورد در بخش رسمی Discussions.
4. **ساخت ایندکس از پلاگین‌های خودتان**: ابزار `apps/plugin-market-generator` در سورس برای ساخت ایندکس است — راه تمیز برای تیم‌ها و سازمان‌ها که می‌خواهند «بازار خصوصی» پلاگین داشته باشند.

## چک‌لیست قبل از انتشار

- [ ] `dsh.bundle` در مانیفست هست و `cordis.patch.yml` در فیلد `files` آمده؟
- [ ] `engines.dsh` اعلام شده؟
- [ ] `npm pack` زده‌اید و محتوای تاربال را بازبینی کرده‌اید؟ (بدون فایل‌های زائد، بدون کلیدها)
- [ ] نصب از تاربال در یک پروفایل تمیز (`--from-default-profile`) تست شده؟
- [ ] `description` ابزارها به انگلیسی واضح نوشته شده؟ (مدل‌ها با انگلیسی بهتر تصمیم می‌گیرند؛ UI می‌تواند فارسی باشد)
- [ ] README با مثال نصب و استفاده؟
- [ ] مجوز مشخص؟ (MIT سازگار با پروژه اصلی)
- [ ] هیچ راز/کلیدی در کد یا تاریخچه گیت نیست؟

## نسخه‌بندی و نگه‌داری

- چون dsh سریع تغییر می‌کند، تغییرات Breaking احتمالی را با محدوده `engines.dsh` ببندید و برای هر نسخه بزرگ dsh، سازگاری را تست و نسخه جدید پلاگین را منتشر کنید.
- تغییرات را با changelog مستند کنید؛ کاربران از طریق `plugin_manager` می‌توانند نصب‌های موجود را ارتقا دهند (پروفایل‌های زنده تغییرات را بلافاصله اعمال می‌کنند).
- اگر الزام نسخه برآورده نشود، نصب بسته می‌شود؛ «معافیت نسخه» فقط با آگاهی از ریسک خرابی و از‌دست‌رفتن داده به کاربر بدهید — این رفتار حفاظتی خود پروژه است، سعی نکنید دورش بزنید.
