# آموزش ۰۷ — تست و دیباگ

وقتی چیزها طبق انتظار پیش نمی‌روند — پلاگین لود نمی‌شود، ابزار رفتار عجیب دارد یا پروفایل بالا نمی‌آید — این آموزش نقشه شماست. منابع اصلی: [مستند تست رسمی](../dsh/docs/testing.md) و ابزارهای بازرسی خود پروژه.

## لایه ۱ — دیباگ پروفایل: «چه چیزی واقعاً بوت شد؟»

مفیدترین فرمان برای شروع:

```sh
dsh --profile web --dump-config
```

درخت کامل ترکیب را چاپ می‌کند: کدام باندل‌ها به چه ترتیبی، کدام پلاگین‌ها insert/override شده‌اند و پیکربندی نهایی هر پلاگین چیست. اگر پلاگینی که انتظارش را داشتید نیست، مشکل در «لایه‌بندی» است نه در کد — لایه بعدی از لایه قبلی override می‌شود و ترتیب مهم است.

دو فرمان مکمل:

```sh
dsh --dump-config-schema   # شِمای JSON سطرهای پروفایل و پچ‌ها بدون بوت
dsh --dump-default-config  # درخت بدون لایه کاربر و --patch — مقایسه با نسخه کامل، لایه شما را ایزوله می‌کند
```

الگوی دیباگ پیشنهادی: خروجی `--dump-default-config` را با `--dump-config` مقایسه کنید تا دقیقاً ببینید لایه‌های شما چه تغییری ایجاد کرده‌اند.

## لایه ۲ — بازرسی زمان اجرا با Cordis

وقتی ترکیب درست است اما رفتار درست نیست، به بازرسی زمان اجرا نیاز دارید:

- در «حالت سازنده» (Creator mode)، دو ابزار فقط‌خواندنی `cordis_inspect_list` و `cordis_inspect_query` به مدل داده می‌شوند؛ می‌توانید مستقیم از عامل بخواهید وضعیت سرویس‌ها را گزارش کند: «با cordis_inspect_list نشان بده کدام پلاگین‌ها فعال‌اند».
- ابزار inspect، ثبت‌نام بازرسی را از رانر میزبان می‌گیرد؛ پرس‌وجوهای کلاینت به صفحه متصل نیاز دارند — یعنی برای دیباگ وب، مرورگر باز و متصل باشد.
- نکته مهم: بازرسی فقط‌خواندنی است. تغییر پایدار را به‌شکل باندل بسازید و با `plugin_manager` نصب کنید، نه از طریق دست‌کاری زمان اجرا.

## لایه ۳ — لاگ‌ها و رخدادها

- **headless بهترین دوست دیباگر است**: `dsh headless --json "..."` تمام رخدادهای اجرا (فراخوانی ابزار، نتایج، تصمیم‌ها) را به‌شکل JSONL روی stdout می‌دهد. یک فراخوانی بگیرید و فایل را با `jq` یا خود dsh تحلیل کنید.
- **پرس‌وجوی نشست**: ابزارهای `session_search`، `session_event_read` و `session_event_trace` تاریخچه کامل رویدادها را می‌دهند — عالی برای «آخرین بار که این ابزار صدا زده شد، دقیقاً چه ورودی/خروجی داشت؟».
- **رویدادهای fs**: پلاگین‌های فایل‌سیستم رویدادهای `fs/observed` و `fs/write-intent` منتشر می‌کنند؛ در رابط وب می‌توانید ببینید عامل چه چیزی را خوانده/نوشته — برای ردیابی ویرایش‌های ناخواسته.

## لایه ۴ — تست‌های پروژه (برای توسعه‌دهندگان سورس)

اگر از سورس این مخزن کار می‌کنید، کل پروژه با **vitest** تست می‌شود. فرمان‌های کلیدی (طبق مستند رسمی testing):

```sh
pnpm test            # تست‌های واحد
pnpm run build       # قبل از تست‌های یکپارچه، build لازم است
pnpm test:e2e        # تست‌های انتها-به-انتها
pnpm test:snapshot   # تست‌های snapshot
pnpm test:bench      # بنچمارک
```

نکات عملیاتی:

- برخی تست‌ها به build artifact تکیه دارند؛ اول `pnpm run build` بزنید.
- تست‌های وب و تست فشار (`test:web`، `test:web-stress`، `test:web-perf`) مخصوص رابط وب هستند و بهتر است فقط برای تغییرات رابط اجرا شوند.
- اگر تست‌هایی که فایل دانلود می‌کنند (وابستگی‌های native) خطای شبکه گرفتند، مشکل شما شبکه است نه تست — متغیرهای پروکسی را بگذارید (آموزش ۰۹).
- فایل‌های snapshot تحت `snapshots/` مدیریت می‌شوند؛ تغییر رفتار عمدی یعنی به‌روزرسانی snapshot در همان commit، نه حذف تست.

## لایه ۵ — دیباگ پلاگین خودتان

الگوی پیشنهادی برای پلاگین‌نویس (از ساده به پیچیده):

1. **آیا اصلاً لود شد؟** پیام `console.log` اول `apply` را ببینید. اگر نیامد: مسیر فایل patch، نام بسته در `cordis.patch.yml` و کلید `dsh.bundle` را چک کنید. یادتان باشد بسته بدون `dsh.bundle` فقط به‌عنوان وابستگی ساده نصب می‌شود و لایه‌ای فعال نمی‌کند.
2. **آیا ابزار ثبت شد؟** در مکالمه بپرسید «فهرست ابزارهای در دسترس تو چیست؟» یا با `cordis_inspect_list` وضعیت را ببینید. اگر ابزار نیست: `inject` را چک کنید (بدون `['tools']` ممکن است قبل از آماده شدن رجیستری صدا شوید) و ترتیب لایه‌ها را.
3. **آیا مدل صدا می‌زند؟** اگر ابزار هست اما مدل سراغش نمی‌رود، مشکل `description` شماست — دقیق‌تر و جهت‌دهنده‌تر بنویسید (مثل توصیف‌های کاتالوگ رسمی).
4. **خطای اجرا؟** خروجی `execute` را ساده و ساختاریافته برگردانید؛ خطاها را به‌صورت پیام قابل‌فهم برگردانید نه exception خام — مدل با پیام تمیز می‌تواند خودش اصلاح کند.
5. **شِمای پارامتر**: از قابلیت infer خودکار `defineTool` استفاده کنید و `required` را حداقلی نگه دارید؛ هر پارامتر اضافی یک نقطه خطای مدل است.

## خطاهای رایج و معنی آن‌ها

| علامت | علت محتمل | درمان |
|---|---|---|
| پلاگین لود نمی‌شود، بدون پیام | فایل patch اشتباه یا بسته پیدا نمی‌شود | مسیر `--patch` و فیلد `name` سطر پلاگین |
| `engines.dsh` راضی نیست | ناسازگاری نسخه باندل و dsh | یا dsh را به‌روز کنید یا محدوده نسخه باندل را اصلاح |
| ابزار در فهرست هست اما خطای اجرا | وابستگی runtime پلاگین نبود | `dsh plugin --profile <name> why <pkg>` |
| وب بالا نمی‌آید / پورت اشغال | پروسه قدیمی هنوز زنده است | پروسه قبلی را ببندید؛ پورت را با `--help` چک کنید |
| مدل ابزار را صدا نمی‌زند | توصیف ضعیف یا ابزار غیرمرتبط | بازنویسی description |
| خطاهای شبکه هنگام نصب/دانلود | تحریم/فیلترینگ، نه باگ پروژه | آموزش ۰۹ |

## پس از رفع مشکل: چرخه بازبینی

چون پروژه پیش‌نمایش توسعه‌دهنده است و تغییرات ناسازگار دور از انتظار نیست، بعد از هر به‌روزرسانی dsh:

1. `--dump-config` بگیرید و با نسخه قبلی مقایسه کنید.
2. یک وظیفه headless ساده تست کنید: `dsh headless "ابزارهایت را لیست کن"` (رفتار دود).
3. تست پلاگین‌های خودتان را اجرا کنید.
4. [راهنمای ارتقا رسمی](../dsh/docs/upgrade-guide/) را اگر موجود است مرور کنید.
